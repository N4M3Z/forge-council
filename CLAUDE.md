# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

forge-council is a pure-markdown multi-agent orchestration framework. Specialist agents run structured 3-round debates (Initial Positions, Challenges, Convergence) organized into councils (DebateCouncil, DeveloperCouncil, ProductCouncil, KnowledgeCouncil, HiringCouncil) plus standalone use. No compiled code -- only markdown agent definitions, YAML configuration, and council orchestration skills. Deployment is handled by the external `forge` CLI.

## Build & Test

```sh
make install         # deploy agents, skills, and rules to all providers
make validate        # run pre-commit checks (prek -> forge -> validate.sh)
make clean           # remove build/ artifacts
```

Pre-commit cascade: `prek run --all-files` -> `forge validate .` -> hash-verified `validate.sh`. Activated by `make install` (sets `core.hooksPath` to `.githooks`). prek config in `.pre-commit-config.yaml`.

## Architecture

```
agents/           specialist markdown files (frontmatter + structured body)
skills/           council orchestration skills (DebateCouncil, DeveloperCouncil, ProductCouncil, KnowledgeCouncil, HiringCouncil)
rules/            AgentTeams.md, LearningCapture.md (always-loaded behavioural rules)
defaults.yaml     canonical agent roster, tool/model assignments, provider model tiers
config.yaml       user overrides (gitignored), same structure as defaults
module.yaml       module metadata (name, version, description)
.claude-plugin/   plugin.json manifest for Claude Code plugin discovery
.githooks/        pre-commit hook calling prek/forge/validate.sh
.github/workflows quality.yaml CI pipeline (prek-action)
```

Platform directories (`.claude/`, `.gemini/`, `.codex/`, `.opencode/`) are generated by `make install` and gitignored. Source of truth is `agents/`, `skills/`, `rules/`, and `defaults.yaml`.

### How Councils Work

Skills define the orchestration. The main session IS the moderator (never spawn a separate moderator). Flow: Step 0 gate check (agent teams env var) -> parse input -> select roster (max 7) -> spawn team (`TeamCreate` + parallel `Task`) -> 3 rounds -> synthesize verdict + teardown (`shutdown_request` -> `TeamDelete`). If agent teams are unavailable, Step 7 falls back to sequential `Task` calls.

Parallel execution requires `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in `~/.claude/settings.json` env. The deployed `rules/AgentTeams.md` documents the gate, mandatory teardown, and known upstream agent-team bugs (#49671, #53160, #55824, #59717).

### Agent Files (`agents/*.md`)

YAML frontmatter with required keys: `name` (PascalCase, matches filename), `description` (pattern: `"Role -- capabilities. USE WHEN triggers."`), `version`.

Deployment config (model, tools) lives in `defaults.yaml`, not in agent frontmatter. Agent files contain only identity (name, description, version) and body instructions.

Body structure in order: blockquote summary (ends with "Shipped with forge-council."), `## Role`, `## Expertise`, `## Personality` (optional), `## Instructions`, `## Output Format`, `## Constraints`.

Constraints must include the honesty clause ("If X is solid, say so") and team communication clause ("communicate findings to the team lead via SendMessage when done"). Every critique must include a concrete suggestion.

### Skill Files (`skills/*/SKILL.md`)

`SKILL.md` contains orchestration instructions plus frontmatter (`name`, `description`, `version`, `argument-hint`). Council skills follow numbered steps Step 1 through Step 7. Debate modes detected from user keywords: checkpoint (default), autonomous ("fast"), interactive ("step by step"), quick ("quick check").

### Rules (`rules/*.md`)

Always-loaded behavioural instructions:

- `AgentTeams.md`: gate-check protocol, mandatory teardown, known upstream bugs around `TeamCreate` / `TeamDelete` / `shutdown_request`.
- `LearningCapture.md`: post-teardown agent that spawns a `general-purpose` Task to distill verdicts into reusable `.claude/rules/` entries.

### Configuration

- `defaults.yaml`: canonical agent roster, tool/model assignments per agent, provider model tiers. Edit when adding or removing agents.
- `config.yaml`: user overrides, gitignored. Same structure as defaults, only the fields you change.
- `module.yaml`: module metadata. Bump `version` on releases.

## Conventions

### Naming

| Context | Convention |
|---------|-----------|
| Agent filenames / name | PascalCase (`SecurityArchitect.md`) |
| Skill directories | PascalCase (`DeveloperCouncil/`) |
| Rule filenames | PascalCase (`AgentTeams.md`) |
| YAML keys | lowercase |
| Team names (runtime) | lowercase-kebab (`dev-council`) |

### Markdown Style

Em-dashes (`--`) in prose. `description` pattern: `"Role -- capabilities. USE WHEN triggers."`. No trailing whitespace. Files end with a newline.

### Git

Conventional Commits: `type: description`. Lowercase, no trailing period, no scope. Types: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`.

## Modification Workflows

**Add agent**: Create `agents/Name.md` with frontmatter + structured body -> add `agents.Name` entry to `defaults.yaml` -> `forge assemble` to preview -> `make install` to deploy -> commit `feat: add Name for [domain]`.

**Modify skill**: Edit `skills/Name/SKILL.md` -> keep numbered step structure intact -> council roster lives inside the skill, not in `defaults.yaml` -> test with a council invocation.

**Update model/tools**: Edit `defaults.yaml` (or `config.yaml` override) -> `make install` -> restart session.
